Provenance Graphs

From Zero to Hero — A complete guide to system causality, forensic tracing, and graph-based security

Part I — Foundations

Day 1–2: What provenance is, what it’s made of, and why causality matters.

1. What is Provenance?

Definition

Provenance (from Latin provenire, "to come forth") is a record of the origin and complete causal history of an object. In computing, it answers: who created this data, how was it derived, and what chain of events led to the current state?

A Brief History of Provenance

Provenance tracking did not start in cybersecurity. The concept evolved through three waves:

  1. Art & Archival Science (centuries old): Museums track the ownership history of paintings to verify authenticity. If a Rembrandt was owned by a known collector in 1780, then by a gallery in 1850, then donated to a museum in 1920, that chain is its provenance. Gaps in the chain raise forgery concerns.
  2. Database & Scientific Workflows (1990s–2000s): Researchers needed to track how a dataset was derived. If a climate model's output depends on satellite data → interpolation algorithm → statistical correction, that derivation chain is provenance. The W3C standardized this as PROV-DM (Provenance Data Model) in 2013.
  3. Operating System Security (2010s–present): Security researchers realized that OS audit logs naturally form provenance records. Every read(), write(), fork(), and connect() system call is a causal event linking system entities. DARPA's Transparent Computing (TC) program (2015–2020) funded major research into OS-level provenance for threat detection.

Why Provenance Matters in Security

A traditional security alert tells you what happened: 

ALERT: Suspicious write to C:\Windows\System32\malware.dll
       Process: cmd.exe (PID 4812)
       Time: 2024-03-15 14:23:07 UTC

This is a point event. It tells you nothing about how we got here. An analyst must now manually search through potentially millions of log entries to reconstruct the attack. This is slow, error-prone, and doesn't scale.

A provenance graph, by contrast, gives you the complete causal chain in one structure: 

invoice.docx ──READ──▶ word.exe ──FORK──▶ cmd.exe ──WRITE──▶ malware.dll
                                            │
                                            ├──CONNECT──▶ 192.168.1.100:443
                                            └──WRITE──▶ HKLM\...\Run

Now the analyst instantly sees: the infection started with a malicious document, which spawned a shell, which then established command-and-control, dropped a payload, and set up persistence. All from one graph query.

Key Insight

The fundamental shift from logs to provenance is from "what events happened" to "what caused what". Logs are a flat timeline. Provenance is a causal structure.

The Three Questions Provenance Answers

Every security investigation boils down to three questions. Provenance graphs can answer all three:

  1. Root Cause: "How did we get compromised?" → Follow edges backward.
  2. Impact: "What did the attacker touch?" → Follow edges forward.
  3. Attribution: "Which entity is responsible?" → Identify the source node of the causal chain.
Think About It

Imagine you are an incident responder. You discover that a server's /etc/passwd was modified. With just logs, how many log entries might you need to search? With a provenance graph, how many hops backward would give you the root cause?

Provenance vs. Related Concepts

Students often confuse provenance with similar terms. Here's how they differ:

Concept What it records Structure
Audit Log Individual events in chronological order Flat list (ordered by time)
Call Graph Which functions call which functions Graph (but no data flow, no timestamps)
Control Flow Graph Execution paths through a program Graph (intra-process only)
Provenance Graph Causal relationships between system entities over time Directed graph with timestamps (acyclic at the event level)
Key Takeaway

Provenance is a system-wide, timestamped, causal record. It captures not just events, but the dependencies between events across processes, files, and the network.

Subjects vs. Objects

The CDM makes an important distinction:

  • Subjects are entities that perform actions. In practice, subjects are almost always processes (or threads). They are the "actors" in the graph.
  • Objects are entities that are acted upon. Files, sockets, registry keys, and memory regions are objects. They are passive — they don't initiate events.
Formal Notation

In the provenance literature, you'll often see: subject ⟶ operation ⟶ object
For example: cmd.exe ⟶ WRITE ⟶ malware.dll

Node Attributes

Each node carries metadata that enriches the graph. The exact attributes depend on the audit system, but common ones include:

Node TypeKey AttributesWhy They Matter
Process PID, executable path, command line, user, parent PID The command line reveals attacker intent (e.g., cmd.exe /c powershell -enc ...)
File Path, hash (SHA-256), size, permissions The hash allows matching against known malware signatures
Socket IP address, port, protocol (TCP/UDP) IP + port identifies C2 servers or exfiltration endpoints
Registry Key path, value name, value data Certain keys (e.g., HKLM\...\Run) indicate persistence mechanisms
Memory Base address, size, protection flags Executable memory regions can indicate code injection

Node Identity & Versioning

A subtle but important point: a file like /tmp/data.csv may be written to multiple times. Is it the "same" node each time? There are two approaches:

  • Whole-object versioning: Every write creates a new version of the file node. The graph has data.csv_v1, data.csv_v2, etc. This is more precise but creates more nodes.
  • Single-object: The file is one node, and edges carry timestamps to distinguish events. Simpler but can lose precision about which version of the file was read.
Think About It

A web server process handles 10,000 requests per day, each reading index.html. Under the versioning approach, how many READ edges would exist between the process and the file? What are the trade-offs of each approach for storage vs. precision?

Key Takeaway

Nodes in a provenance graph are typed system entities with rich metadata. The subject/object distinction determines the direction of causality: subjects act, objects are acted upon.

3. System Events: The Edges

Edges are the most important part of a provenance graph. Each edge represents a single system event — an action performed by a subject on an object at a specific time.

Edge Types in Detail

The CDM defines over 20 event types in total, but 9 are most relevant to security analysis. Understanding each one is critical because the edge type determines the direction of information flow, which is not always the same as the direction of causality:

Edge Type Meaning Information Flow Example
READ Process reads from a file File → Process cat /etc/passwd
WRITE Process writes to a file Process → File echo "data" > out.txt
EXECUTE Process executes a binary File → Process ./malware.bin
FORK / CLONE Process creates a child process Parent → Child fork() system call
CONNECT Process opens a network connection Process → Socket connect(sockfd, addr)
SEND Process sends data over network Process → Socket send(sockfd, data)
RECEIVE Process receives data from network Socket → Process recv(sockfd, buf)
MMAP Process maps a file into memory File → Memory Loading a shared library (.dll/.so)
RENAME / LINK Process renames or links a file Process → File mv old.txt new.txt

Information Flow vs. Edge Direction

This is a source of confusion for beginners. Consider a READ event:

Common Pitfall

When cat reads passwords.txt, the action goes from process to file (the process initiates the read), but the information flows from file to process (data enters the process). Different papers use different conventions:

  • Action-directed: Edge points from the entity that initiates the event. READ: process → file.
  • Flow-directed: Edge points in the direction that data flows. READ: file → process.

Most modern provenance systems (DARPA TC, KAIROS, SPADE, CamFlow) use flow-directed edges, because information flow is what matters for tracking how data (and compromise) propagates.

Edge Attributes

Each edge carries metadata beyond its type:

  • Timestamp: The exact time the event occurred (nanosecond precision in many audit systems). This enables temporal ordering.
  • Sequence number: A monotonically increasing counter that resolves ordering ambiguities when timestamps collide.
  • Size: For read/write events, the number of bytes transferred.
  • Return code: Whether the system call succeeded or failed.

Multiplicity: Multiple Edges Between the Same Nodes

In real provenance graphs, you often see multiple edges between the same pair of nodes. For example, a process might read the same file 1,000 times. Each read is a separate edge with a different timestamp.

This is important because it means provenance graphs are multigraphs (multiple edges between the same pair), not simple graphs. Some systems address this by aggregating repeated edges into a single edge with a count, trading precision for compactness.

Concrete Example

A Python script reads a CSV file line by line in a loop. The audit system records 10,000 READ events from python3 to data.csv. In the raw graph, this is 10,000 parallel edges. After aggregation, it becomes one edge labeled READ × 10,000.

Think About It

If a process writes to a file 5 times with different data each time, and another process later reads that file, which write is the read dependent on? The last write? All of them? How does this affect backward tracing accuracy?

Key Takeaway

Edges represent timestamped system events. The direction encodes information flow (not just action initiation). Real graphs are multigraphs with potentially millions of parallel edges.

4. Causality & Temporal Ordering

Causality is the intellectual core of provenance. Without it, a provenance graph would just be "things that happened" — no different from a log. Causality gives the graph its meaning.

Definition — Causal Dependency

Event B is causally dependent on Event A (written A ≺ B) if and only if:

  1. A occurred before B (temporal precedence), AND
  2. The output of A was available as input to B (data dependency).

This is formalized as the happens-before relation (Lamport, 1978).

Why Both Conditions Are Needed

Temporal precedence alone is not enough. Consider:

  • At t=1, Process A writes to file_X.txt
  • At t=2, Process B writes to file_Y.txt

A happened before B, but they are not causally related — they touched different objects. There is no information flow from A to B.

Now consider:

  • At t=1, Process A writes to config.ini
  • At t=2, Process B reads from config.ini

Here, A happened before B and B consumed A's output (the data in config.ini). B is causally dependent on A. This dependency is visible in the provenance graph as the path: 

Process A ──WRITE──▶ config.ini ──READ──▶ Process B

Transitive Causality

Causality is transitive: if A caused B and B caused C, then A transitively caused C. This is what makes provenance graphs so powerful — you can trace multi-hop chains. 

email.exe ──READ──▶ attachment.zip ──WRITE──▶ dropper.exe ──EXECUTE──▶ payload.exe ──READ──▶ secret.doc ──SEND──▶ exfil:443

The exfiltration of secret.doc is transitively caused by opening the email attachment, even though five hops separate them. (Note: the attachment is extracted to dropper.exe via a WRITE, then the dropper is executed.)

The DAG Property (at the Event Level)

Because causality requires temporal precedence (the cause must happen before the effect), provenance graphs are acyclic at the event level — each individual event edge is unique in time and cannot form a cycle. However, at the entity level, the same pair of nodes (e.g., a process and a file) can be connected by multiple edges in both directions over time, which may appear cyclic when timestamps are ignored.

Formally:

  • Directed: Every edge has a source and a destination (the cause and the effect).
  • Acyclic: Following edges forward will never return you to a node you've already visited.
Why No Cycles?

In theory, a process could read a file it previously wrote, creating a logical cycle (process → file → process). But in a provenance graph, timestamps break this: the write edge has timestamp t=1 and the read edge has timestamp t=2. These are different events, not a cycle. The graph may have the same entities appearing multiple times, but the event edges always move forward in time.

Information Flow Tracking (Taint Propagation)

Causality enables a powerful technique called taint propagation. The idea:

  1. Mark a suspicious entity as "tainted" (e.g., a downloaded file from a phishing email).
  2. Propagate the taint forward along all causal edges.
  3. Every entity reachable from the tainted source is potentially compromised.

This is the conceptual basis of forward analysis (impact assessment). In reverse, you can start from a suspicious event and propagate backward to find the original source of compromise — that's backward analysis (root cause).

Taint Example

A user downloads update.exe from a suspicious URL. We taint that file. The provenance graph shows:

update.exe ──EXECUTE──▶ updater.exe ──FORK──▶ svchost.exe ──WRITE──▶ keylog.dat
                                                    │
                                                    └──SEND──▶ 10.0.0.5:8080

The taint propagates from update.exe through every node on the right. All five entities are marked as potentially compromised.

Happens-Before: The Formal Foundation

Leslie Lamport's happens-before relation (1978), originally developed for distributed systems and logical clocks, provides a useful conceptual foundation. While provenance systems typically rely on physical timestamps rather than logical clocks, the same principles apply:

  • If event a and event b are in the same process, and a comes first, then a → b.
  • If event a is the sending of a message by one process, and event b is the receipt of that message by another, then a → b.
  • If a → b and b → c, then a → c (transitivity).

Events that are not related by → are concurrent — they happened independently with no causal connection.

Key Takeaway

Causality = temporal precedence + data dependency. It's transitive, which enables multi-hop tracing. The happens-before relation formalizes this. Taint propagation is causality in action.

5. The Data Model: From Events to Graph

We now understand nodes (entities) and edges (events). But how does a raw audit event become a graph edge? This section covers the conceptual pipeline.

The Triple: The Atomic Unit

Every provenance edge can be expressed as a triple:

Subject — Event Type —▶ Object

With metadata attached: 

(subject: cmd.exe/PID=4812, event: WRITE, object: malware.dll, time: 14:23:07, bytes: 65536)

What Generates These Triples?

The raw data comes from OS-level audit frameworks. These hook into the kernel to intercept system calls:

OSAudit FrameworkWhat It Captures
Linux Linux Audit (auditd) System calls: open, read, write, execve, fork, connect, etc.
Windows ETW (Event Tracing for Windows) File, registry, process, network events via providers
macOS Endpoint Security Framework Process, file, network events

Each framework produces structured log entries. The provenance system's job is to parse these entries and construct the graph by:

  1. Identifying the subject: Which process initiated the event? (PID, thread ID)
  2. Identifying the object: What entity was acted on? (file path, socket address, registry key)
  3. Classifying the event: Is this a READ, WRITE, FORK, CONNECT, etc.?
  4. Creating or updating nodes: If the entity doesn't exist in the graph yet, create it.
  5. Creating the edge: Link subject to object with the event type and timestamp.

DARPA TC: The Common Data Model (CDM)

The DARPA Transparent Computing program (2015–2020) funded five research teams to build provenance-based threat detection systems. To enable interoperability, they defined the CDM — a standardized schema for provenance data.

CDM defines:

  • 5 entity types: Subject (process), FileObject, NetFlowObject, SrcSinkObject (registry, IPC), MemoryObject
  • 13 core event types (most relevant to security): READ, WRITE, EXECUTE, FORK, CLONE, CONNECT, ACCEPT, SEND, RECEIVE, MMAP, RENAME, LINK, UNLINK. (The full CDM schema defines additional event types such as OPEN, CLOSE, SIGNAL, MODIFY_FILE_ATTRIBUTES, etc.)
  • Standard attributes: UUIDs for entities, timestamps, sequence numbers, properties maps
CDM Event Example
{
  "datum": "com.bbn.tc.schema.avro.cdm20.Event",
  "type": "EVENT_WRITE",
  "timestampNanos": 1521100000000000,
  "subject": "UUID-process-cmd-4812",
  "predicateObject": "UUID-file-malware-dll",
  "size": 65536
}

This single record becomes one edge in the provenance graph.

From Raw Logs to Graph: A Walkthrough

Let's trace how four raw audit events become a subgraph:

t=001
auditd: execve(pid=100, exe="/bin/bash")
→ Create process node bash:100
t=002
auditd: open(pid=100, path="/etc/config", flags=O_RDONLY)
→ Create file node /etc/config, add edge bash:100 ←READ← /etc/config
t=003
auditd: fork(parent=100, child=101)
→ Create process node child:101, add edge bash:100 →FORK→ child:101
t=004
auditd: connect(pid=101, addr=10.0.0.5, port=443)
→ Create socket node 10.0.0.5:443, add edge child:101 →CONNECT→ 10.0.0.5:443

The resulting subgraph:

/etc/config ──READ──▶ bash:100 ──FORK──▶ child:101 ──CONNECT──▶ 10.0.0.5:443

Graph Construction Decisions

Building the graph involves design decisions that affect analysis quality:

  • Granularity: Track every system call, or only security-relevant ones? More granularity = more edges = better precision but higher storage cost.
  • Entity resolution: How to handle process reuse (PID recycling), file renames, and hardlinks? Two different paths pointing to the same inode should be the same node.
  • Batching vs. streaming: Build the graph after collecting all events (batch), or add edges as events arrive (streaming)? Real-time EDR requires streaming.
Key Takeaway

Raw audit events are converted to (subject, event, object) triples and assembled into a graph. The CDM provides a standard schema. Graph construction involves trade-offs between granularity, accuracy, and performance.

7. Forward & Backward Analysis

The two most fundamental operations on a provenance graph are backward tracing (root cause) and forward tracing (impact assessment). These are graph traversals.

Backward Tracing: Root Cause Analysis

Definition

Backward tracing from node v computes all nodes that are ancestors of v in the provenance graph — i.e., all nodes u such that there exists a directed path from u to v.

In security terms: given a suspicious event (e.g., data exfiltration), backward tracing finds every entity that contributed to it. The root of this subgraph is the initial compromise vector.

Forward Tracing: Impact Assessment

Definition

Forward tracing from node v computes all nodes that are descendants of v — i.e., all nodes w such that there exists a directed path from v to w.

In security terms: given a compromised entity (e.g., a process running attacker code), forward tracing finds everything it touched.

Path Queries & Reachability

Beyond simple ancestor/descendant sets, provenance graphs support richer queries:

  • Reachability: "Can data from node A ever reach node B?" — Is there a directed path from A to B?
  • Shortest path: "What is the most direct causal chain from A to B?"
  • All paths: "What are all the ways A could have influenced B?" (There may be multiple attack paths.)
  • Subgraph extraction: "Give me the complete subgraph between the initial compromise and the data exfiltration." This is the attack story.
Real-World Usage

DARPA's TC Engagement 3 (2018) tested provenance systems against realistic APT scenarios. Analysts used backward tracing from detected alerts to reconstruct complete attack campaigns spanning hundreds of events across multiple hosts. The provenance graph reduced investigation time from hours to minutes.

Key Takeaway

Backward tracing finds root causes. Forward tracing assesses impact. Together, they reconstruct the complete attack narrative from any starting point in the graph.

Part III — Real-World Challenges

Day 5–6: Why provenance is hard, and the open research problems.

9. The Dependency Explosion Problem

So far, our examples have been small and clean. Real provenance graphs are not. A single Linux server running for one day can produce millions of audit events and tens of millions of graph edges. The central challenge of provenance is dependency explosion.

Definition

Dependency explosion occurs when backward or forward tracing from a single node returns an impractically large subgraph, often including most of the system's entities. The result is so large that it's useless for investigation — everything appears connected to everything.

Why It Happens: Long-Running Processes

The root cause is long-running processes that interact with many entities. Consider:

  • An Apache web server runs for days, handling thousands of requests. It reads every served file (index.html, style.css, images...) and receives data from every client.
  • A system logger (syslog) writes to a log file that is read by monitoring tools, creating a path from every logged event to every monitoring dashboard.
  • bash reads /etc/profile, .bashrc, and shared libraries at startup. Every command you run in that bash session is causally connected to those initial reads.

The Numbers

Research studies on the DARPA TC dataset report:

  • A single host running for 2 weeks produces ~40 million audit events.
  • The resulting provenance graph has millions of nodes and tens of millions of edges.
  • A backward trace from a single alert can return thousands of nodes — far too many for a human analyst to examine.

Approaches to Mitigate Explosion

Researchers have proposed several strategies:

1. Execution Partitioning

Instead of treating a long-running process as one node, split it into smaller units based on high-level events (e.g., each HTTP request creates a new "unit" of the Apache process). This breaks false dependencies between unrelated requests.

2. Tag Propagation & Prioritization

Assign information flow tags to data and track how tags propagate through the graph. When tracing backward, only follow edges whose tags match the alert's tag. This prunes irrelevant branches.

3. Anomaly-Based Pruning

Score each edge by how unusual it is (compared to a baseline model). During tracing, prioritize high-anomaly edges and ignore routine ones (e.g., a process reading a shared library it always reads).

4. Graph Summarization

Compress the graph by merging repeated patterns. If a process reads the same 100 files every day, collapse those into a single "pattern node" during normal operation, and expand only when anomalies are detected.

Think About It

Execution partitioning can reduce false dependencies, but it can also break true dependencies if the partition boundaries don't align with actual information flow. How would you decide where to place partition boundaries?

Key Takeaway

Dependency explosion is the #1 practical challenge of provenance graphs. Long-running processes create false causal connections that make traces useless. Mitigation strategies include execution partitioning, tag propagation, anomaly-based pruning, and graph summarization — each with its own trade-offs.

10. Graph Properties & Metrics

Understanding the structural properties of provenance graphs helps you reason about their behavior and design better analysis algorithms.

Degree Distribution

The degree of a node is the number of edges connected to it. In provenance graphs:

  • In-degree (incoming edges): How many entities contributed data to this node.
  • Out-degree (outgoing edges): How many entities this node sent data to.

Provenance graphs typically follow a power-law distribution (as observed by Han et al. in UNICORN, 2020): most nodes have very few edges, but a small number of "hub" nodes have extremely many. These hubs are usually long-running system processes (init, systemd, svchost.exe).

Fan-In and Fan-Out

Definitions

Fan-in of a node: the number of distinct source nodes that have edges pointing to it. High fan-in means many entities contribute to this node.

Fan-out of a node: the number of distinct destination nodes that this node has edges pointing to. High fan-out means this node affects many entities.

Security implications:

  • High fan-in + high fan-out: These are the "chokepoint" nodes that cause dependency explosion. Example: svchost.exe on Windows receives data from many sources and sends to many destinations.
  • Low fan-in + high fan-out: A single entity that affects many others. Potentially an attack source (one compromised process touching many files).
  • High fan-in + low fan-out: A data aggregator. Example: a log file that many processes write to.

Graph Density

Density = (number of edges) / (number of possible edges). Provenance graphs are typically very sparse — density well below 0.01. This means most entities don't interact with most other entities, which is expected: a word processor doesn't touch database files.

Sparsity is good news for analysis algorithms: sparse graphs can be stored efficiently and traversed quickly.

Connected Components

A weakly connected component is a maximal set of nodes where every node can reach every other node if you ignore edge direction. In provenance graphs:

  • There is usually one giant component containing the vast majority of nodes (because most processes share libraries, config files, etc.).
  • A few small isolated components represent truly independent activities.

This is another manifestation of the dependency explosion problem: the giant component makes it hard to isolate attack-relevant subgraphs.

Temporal Diameter

The diameter of the graph is the longest shortest path between any two nodes. In provenance graphs, this reflects the maximum number of causal hops in the system. In datasets like DARPA TC, the most complex causal chains can involve dozens of intermediate entities, though the exact diameter depends on system workload and observation period.

Key Takeaway

Provenance graphs are sparse, power-law distributed, mostly connected structures. Fan-in/fan-out analysis identifies both dependency explosion hubs and potential attack sources. Understanding these properties is essential for designing scalable analysis algorithms.

11. Why Graphs Beat Flat Logs

Let's make the comparison rigorous. Here's the same 5-step attack analyzed with logs vs. a provenance graph:

The Log View

14:23:01  word.exe (PID 3001) opened C:\Users\victim\invoice.docx
14:23:02  chrome.exe (PID 2500) connected to google.com:443
14:23:03  word.exe (PID 3001) created process cmd.exe (PID 3002)
14:23:04  svchost.exe (PID 800) wrote to C:\Windows\Temp\update.tmp
14:23:05  cmd.exe (PID 3002) read C:\config.ini
14:23:06  explorer.exe (PID 1200) read C:\Users\victim\Desktop

The attack events are interleaved with benign activity. An analyst must mentally filter out chrome.exe, svchost.exe, explorer.exe, and notepad.exe. With thousands of events per second on a real system, this is impossible to do manually.

The Graph View

The provenance graph automatically connects only causally related events:

                                              │
                                              ├──CONNECT──▶ 192.168.1.100:443
                                              └──WRITE──▶ HKLM\...\Run

The benign activity (chrome, svchost, explorer, notepad) is in a separate part of the graph with no edges connecting to the attack chain. It's automatically excluded.

The Key Advantage

Logs tell you what happened. Graphs tell you why it happened. The structural relationships between entities are the most valuable information for security analysis, and they are invisible in flat logs.

12. Challenges & Open Problems

Provenance graphs are powerful, but the field has significant unsolved challenges:

Challenge 1: Storage & Scalability

A single enterprise host typically generates 1–5 GB of audit data per day, though heavily loaded servers can produce 10+ GB/day (Pasquier et al., 2023). An organization with 10,000 endpoints produces tens of terabytes daily. Storing, indexing, and querying provenance graphs at this scale requires specialized graph databases and compression techniques.

Research directions: lossy compression, tiered storage (hot/warm/cold), stream processing that discards provenance for events classified as benign.

Challenge 2: The Semantic Gap

System calls are low-level. An open() + read() + close() sequence could mean "a user opened a document" or "a malware read a credential file." The provenance graph cannot distinguish intent from mechanism.

This "semantic gap" means analysts must interpret the graph's low-level events in terms of high-level attacker behavior, which requires domain expertise.

Challenge 3: Evasion

Sophisticated attackers can attempt to evade provenance tracking:

  • Direct kernel object manipulation (DKOM): Modify kernel structures to hide processes or connections from the audit system.
  • Mimicry attacks: Make malicious actions look like benign ones (e.g., using explorer.exe to download files instead of powershell.exe).
  • Audit log tampering: Delete or modify audit logs before they are processed.

Countermeasures: hardware-backed audit (Intel PT), append-only log storage, real-time streaming to remote collectors.

Challenge 4: Real-Time Processing

For an EDR system to be useful, it must process events in real time — not hours after an attack. This means the provenance graph must be built, queried, and analyzed as events stream in, with latency measured in seconds.

Research directions: incremental graph algorithms, streaming GNN inference, windowed processing.

Challenge 5: Cross-Host Provenance

APTs often span multiple hosts (lateral movement). Connecting provenance graphs from different machines requires matching network events: a SEND on Host A should link to the corresponding RECEIVE on Host B. This is conceptually simple but practically hard due to clock skew, NAT, and encrypted traffic.

Challenge 6: False Positive Reduction

Anomaly detection on provenance graphs produces false positives. A software update might create unusual process trees that look like an attack. Reducing false positives without missing real attacks is an active research area.

Challenge 7: Ground Truth Scarcity

Most provenance-based detection systems are evaluated on a small number of datasets (primarily DARPA TC Engagements 3 and 5). There is a critical lack of diverse, labeled provenance datasets for training and evaluation. As Goyal et al. (2025) demonstrate, evaluation on limited datasets can overstate the effectiveness of complex models when simpler baselines perform comparably.

Key Takeaway

Provenance graph research is an active field with major open problems in storage, real-time processing, evasion resistance, false positive reduction, and evaluation methodology. These challenges are why this remains an area of active research rather than a solved problem.

Glossary

Provenance

The complete causal history of how a system entity reached its current state.

Subject

An entity that initiates actions — usually a process or thread.

Object

An entity acted upon: file, socket, registry key, or memory region.

Edge / Event

A timestamped, typed, directed link from subject to object (or vice versa, depending on information flow).

DAG (Event-Level)

Directed Acyclic Graph. Each event edge is unique in time, preventing cycles at the event level. Entity-level cycles may appear when timestamps are ignored.

Information Flow

The direction data moves in an event. READ: file→process. WRITE: process→file.

Backward Tracing

Follow edges backward to find all ancestors of a node. Used for root cause analysis.

Forward Tracing

Follow edges forward to find all descendants of a node. Used for impact assessment.

Dependency Explosion

When traces return impractically large subgraphs due to long-running hub processes.

CDM

CDM defines 13 core event types relevant to security analysis; the full schema includes additional types.

Fan-In / Fan-Out

Number of distinct source/destination nodes for a given node. Reveals hubs and potential attack sources.

Taint Propagation

Marking an entity as suspicious and tracking the mark forward through causal edges to assess impact.

Happens-Before

Lamport's partial ordering of events. A→B means A causally precedes B.

Execution Partitioning

Splitting a long-running process into smaller units to reduce false dependencies.

Semantic Gap

The disconnect between low-level system calls and high-level attacker intent.

Chokepoint

A node whose removal would disconnect a significant portion of the attack graph.

The Five Layers

Layer 1 — Endpoints (Data Sources)

These are the actual machines being protected: workstations, servers, containers. Each endpoint runs a lightweight agent that hooks into the OS audit framework:

  • Windows: ETW (Event Tracing for Windows) — captures process, file, registry, and network events via kernel providers.
  • Linux: auditd + Linux Security Modules — intercepts system calls (open, read, write, execve, connect, etc.).

The agent performs minimal processing on the endpoint: it filters obvious noise (e.g., repeated timer events), batches events, and streams them to the central server. The agent must be lightweight to avoid impacting endpoint performance.

Key Design Decision

All heavy computation (graph construction, ML inference, LLM analysis) happens on the server, not the endpoint. This keeps the agent's CPU/memory footprint at a target of < 2%, which is critical for deployment on production machines.

Layer 2 — Ingestion & Graph Construction (Server)

The central server receives event streams from all endpoints. A graph builder component converts raw events into the provenance graph:

  1. Parse: Deserialize raw audit events (JSON, Avro, or binary format).
  2. Normalize: Map OS-specific event types to the CDM schema (e.g., Windows event ID 4688 "A new process has been created" → FORK/EXECUTE, Linux execve → EXECUTE). Note: Event 4688 combines the fork+exec pattern into a single event.
  3. Entity Resolution: Match events to existing nodes (by PID, file path, socket tuple) or create new nodes.
  4. Edge Creation: Create a typed, timestamped edge for each event.
  5. Windowing: Group edges into time windows (e.g., 5-minute or 15-minute windows) for batch processing by the ML model.

Layer 3 — Graph ML Model (Threat Detection)

The core detection engine. A Graph Neural Network (GNN) operates on the provenance graph to identify anomalous behavior. The typical architecture:

ML Pipeline

Training phase (offline, on known-benign data):

  1. Node feature encoding: Each node type gets an embedding vector. Process nodes encode: executable name, user, parent. File nodes encode: extension, path depth, permissions.
  2. Graph encoder (GAT/GCN): A Graph Attention Network aggregates neighborhood information. Each node's embedding is updated based on its neighbors' features and edge types. This captures behavioral context — a process is characterized not just by itself, but by what it reads, writes, spawns, and connects to.
  3. Temporal model (GRU/LSTM): A recurrent layer tracks how node embeddings change over time. Normal processes have stable patterns; compromised processes show sudden shifts.
  4. Edge prediction head: The model learns to predict "given source node and destination node, what edge type should connect them?" During training on benign data, it learns normal patterns.

Inference phase (real-time, on live data):

  1. For each new edge in the graph, the model predicts how likely this edge type is given the source and destination.
  2. If the predicted probability is low → the event is anomalous (unexpected behavior).
  3. An anomaly score is assigned to each edge.
  4. Edges with scores above a threshold are flagged.
  5. Flagged edges are grouped into anomalous subgraphs using connected component analysis within a time window.

The key insight of this approach:

Why Graph ML Works

Traditional EDR uses signature matching ("block known-bad hashes") or rule-based detection ("alert if cmd.exe spawns from word.exe"). Graph ML detects attacks it has never seen before by identifying structural anomalies — unusual patterns of causality, not just individual suspicious events. A novel malware with a unique hash will still create anomalous graph patterns when it reads credentials, connects to external IPs, and writes to persistence locations.

Layer 4 — LLM Forensics (Context & Narrative)

The Graph ML model tells you something anomalous happened. The LLM tells you what it means. This is where the semantic gap (Section 12) gets bridged.

When the ML model flags an anomalous subgraph, the system:

  1. Extracts the subgraph: The anomalous edges plus their surrounding context (1-2 hop neighborhood) are serialized into a structured representation.
  2. Enriches with metadata: Node attributes (file hashes, process command lines, IP geolocation), threat intelligence lookups (known C2 IPs, malware hashes), and historical baseline behavior.
  3. Prompts the LLM: The serialized subgraph + metadata is sent to the LLM with a forensic analysis prompt.

The LLM produces:

Attack Narrative Human-readable description of what happened "A macro in invoice.docx spawned cmd.exe which established C2 with 192.168.1.100 and set up registry persistence."

Layer 5 — Dashboard & Response

The final layer presents results to the security analyst:

  • Alert dashboard: Ranked list of anomalous subgraphs with severity scores.
  • Graph visualization: Interactive provenance subgraph (like the demos in this course).
  • LLM narrative panel: The generated forensic report alongside the graph.
  • Response actions: One-click remediation (kill process, quarantine file, block IP).

The Two-Model Architecture: Why Both ML and LLM?

A common question: why not use just the LLM for everything, or just the GNN?

CapabilityGraph ML (GNN/GAT)LLM
Process millions of edges/sec Yes (designed for it) No (token limits, cost)
Structural pattern detection Yes (native graph reasoning) Limited (must serialize graph to text)
Explain why something is an attack No (outputs a score, not a narrative) Yes (natural language reasoning)
Map to ATT&CK / generate IOCs No Yes (trained on security knowledge)
Suggest remediation No Yes
Run at edge / low latency Yes (small model, fast inference) No (large model, high latency)
The Complementary Roles

The Graph ML model is the fast detector: it processes every edge in real-time and flags anomalies. It answers "is this suspicious?"

The LLM is the slow analyst: it only runs on flagged subgraphs (maybe 5-10 per day) and produces rich forensic context. It answers "what does this mean, where did it come from, and what should we do?"

Together, they form a two-stage pipeline: fast triage (ML) followed by deep analysis (LLM). This mirrors how human SOC teams work: Tier 1 analysts triage alerts quickly, Tier 2/3 analysts investigate deeply.

Training vs. Inference

The Graph ML model has two distinct phases:

PhaseWhenInputOutputCompute
Training Offline (before deployment, periodic retraining) Provenance graphs from known-benign activity Model weights that encode "normal" behavior GPU, hours to days
Inference Real-time (during deployment) Live provenance graph (streaming edges) Per-edge anomaly scores GPU or CPU, milliseconds per batch

The LLM is not trained on your provenance data — it uses a pre-trained foundation model (e.g., Claude, GPT-4) with in-context learning. The anomalous subgraph is serialized into the prompt along with instructions for forensic analysis. This means:

  • No fine-tuning required (use the LLM as-is)
  • The LLM's security knowledge comes from its pre-training data (security papers, ATT&CK documentation, incident reports)
  • You can switch LLM providers without retraining

Key Takeaway

A graph-based EDR system has five layers: Endpoint Agents (data collection) → Graph Builder (event → graph) → Graph ML (fast anomaly detection) → LLM Forensics (deep analysis & narrative) → Dashboard (human review & response).
