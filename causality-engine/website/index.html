Understanding the
Ophanim-EDR Causality Engine

An interactive guide to how graph neural networks detect cyber attacks by learning what "normal" looks like — and flagging everything else.

The Challenge

Why can't antivirus catch advanced attacks?

Traditional security tools look at individual files or events in isolation. But sophisticated attackers chain together dozens of legitimate operations to achieve malicious goals — each step looks normal on its own.

🔍

The Needle in a Haystack

A modern enterprise endpoint generates millions of events per day. An APT attack might touch only 50 edges out of 2 million. Finding that 0.0025% is the challenge.

⏱️

The 15-Minute Blind Spot

The best current system (KAIROS) waits until a 15-minute time window closes before making a detection decision. That's 15 minutes for an attacker to establish persistence.

🔄

The Drift Problem

What's "normal" changes over time — new software, new users, seasonal patterns. A static model trained in January becomes inaccurate by March. Current systems can't adapt.

Key Concepts

ML concepts you need to know

Don't worry if you're new to machine learning. Here's each concept explained with everyday analogies.

🕸️

A provenance graph connects every system entity (processes, files, network connections) with directed edges showing "who did what to whom." If chrome.exe writes to cookies.db, that's an edge labeled WRITE from the chrome process node to the cookies file node.

These graphs grow in real time as events happen. A typical enterprise host generates a graph with 690,000+ nodes over a few days.

💡 Analogy: Think of it like a security camera system for your OS — except instead of video frames, it records every interaction between every program, file, and network connection.
🧠

Regular neural networks process fixed-size inputs (like images or text). But our data is a graph with varying numbers of nodes and edges. GNNs solve this through message passing: each node collects information from its neighbors, updates its own representation, and repeats.

After message passing, each node's representation encodes not just its own features, but also the structure of its local neighborhood.

💡 Analogy: Like a neighborhood watch — each person talks to their direct neighbors, forming an understanding of what's happening in their part of the street. After a few rounds of gossip, everyone has a picture of the whole neighborhood.
👁️

A basic GNN treats all neighbors equally. But in security, a process's parent is far more important than a random file it read once. Graph Attention Networks (GAT) learn attention weights — a score for each neighbor saying "how much should I listen to you?"

We use 4 attention heads, each with 16-dimensional attention. Different heads can focus on different types of relationships simultaneously.

💡 Analogy: Imagine you're at a noisy party. You can't listen to everyone equally — you automatically pay more attention to the person saying something important, and tune out the small talk. GAT does this for graph nodes.
🔧

The encoder compresses each node into a compact 64-dimensional representation that captures its identity and relationships. The decoder then tries to predict: "Given these two nodes, does an edge exist between them? If so, what type?"

The model is trained only on benign data. It learns what normal system behavior looks like. When it sees an attack, it fails to reconstruct those edges correctly — and that failure (the reconstruction error) IS the anomaly signal.

💡 Analogy: Like training a bank teller to recognize legitimate signatures. You don't need to show them every possible forgery — you show them thousands of real signatures, and anything that doesn't "look right" gets flagged.
⏳

A Gated Recurrent Unit (GRU) is a type of recurrent neural network that maintains a "hidden state" — a compact summary of everything it's seen so far. Each node in our graph gets its own GRU state that updates every time a new event involves that node.

The "gates" (reset and update) control how much old information to keep vs. how much new information to let in, preventing important long-term patterns from being overwritten by recent noise.

💡 Analogy: Like a detective's notebook for each suspect. Every time the suspect does something new, the detective updates their notes — keeping the important observations and letting go of irrelevant details. The notebook IS the GRU hidden state.
📊

Inverse Document Frequency (IDF) is borrowed from information retrieval. Common words like "the" carry little meaning; rare words like "exfiltration" carry a lot. We apply the same logic to edges: a process→WRITE→file is so common it's boring. A socket→EXECUTE→process is rare and screams "something unusual is happening."

The formula: IDF = log(N / (1 + count)), where N is total training triples and count is how often this specific pattern appeared.

💡 Analogy: In a school, a student walking to class is unremarkable. A student walking backward through the hallway at 3 AM deserves attention. IDF is the "weirdness multiplier."
Architecture Deep-Dive

How data flows through the model

Click each stage to see what it does, why it's designed that way, and what the actual code produces.

① Raw Event Features
heterogeneous: 3–8 dims per CDM node type

Every system entity gets a feature vector based on its type. A process has 8 features (pid, ppid, uid, gid, start_time, cmd_hash, privilege_level, session_id), while a file has only 4 (path_hash, size, permissions, inode).

The challenge: you can't feed vectors of different sizes into the same neural network layer. That's why the next stage exists.

↓
② NodeTypeProjection
6 × nn.Linear → 64-dim common space (~3K params)

Each node type gets its own small nn.Linear layer that projects its raw features to a common 64-dimensional space. After this step, every node — whether process, file, or socket — lives in the same vector space and can be compared directly.

# Process: 8-dim → 64-dim
x_proc = Linear(8, 64)(raw_process_features)
# File: 4-dim → 64-dim
x_file = Linear(4, 64)(raw_file_features)
↓
③ 1-Layer GAT
4 heads × 16-dim = 64-dim · LayerNorm + ELU · k=10

The Graph Attention Network layer performs message passing: each node looks at its up to 10 nearest neighbors, computes attention weights, and updates its embedding. With 4 heads, the model can attend to 4 different types of relationships simultaneously.

Why only 1 layer? Most provenance graph nodes have ≤20 neighbors. A second layer would expand the receptive field to 100 nodes at 10× the computation cost — but those 2-hop neighbors mostly don't exist. So 1 layer is both sufficient and efficient.

↓
④ GRU Cell
64-dim hidden state · per-node temporal memory

Each node maintains a persistent 64-dim hidden state that accumulates temporal context. The GRU's reset gate decides which old information to discard, and the update gate decides how much new information to integrate.

This is the "memory" of the model. A process that was benign yesterday but starts behaving differently today will produce a different GRU state — even if the spatial snapshot (GAT output) hasn't changed dramatically.

↓
⑤ EdgeDecoder (Dual-Head)
concat(z_src, z_dst) = 128-dim → P(exists) + P(type)

For each edge, we concatenate the source and target node embeddings into a 128-dim vector and pass it through a shared MLP trunk, then split into two heads:

Head 1 (Existence): "Should this connection exist at all?" → sigmoid output (0 to 1).

Head 2 (Type): "If it exists, what type of operation is it?" → 9-class classification (WRITE, READ, EXECUTE, FORK_CLONE, CONNECT, SEND, RECEIVE, MMAP, RENAME_LINK).

Two heads catch two types of anomalies: an unexpected connection vs. an unexpected operation type.

↓
⑥ Anomaly Score
raw = BCE + CE · final = raw × IDF(src, edge, dst)

The raw anomaly score is the sum of two losses:

• BCE (Binary Cross-Entropy) — how wrong the existence prediction was

• CE (Cross-Entropy) — how wrong the type prediction was

This raw score is multiplied by the IDF weight of the edge's (source_type, edge_type, destination_type) triple. Rare patterns get amplified; common patterns get damped.

For graph-level scoring, we take the mean of the top 10% highest edge scores — because attacks affect only a small fraction of all edges.

Design Choices

Why these technologies?

Every design decision is backed by published research. Here's what was chosen — and what was rejected.

Spatial Encoder: GAT vs GCN

GAT CHOSEN

~98.3% accuracy on IDS benchmarks. Learns per-edge attention weights — naturally shows which neighbor caused the anomaly. 4 heads × 16-dim = 64-dim output.

📄 Veličković et al., ICLR 2018 · Validated by KAIROS (IEEE S&P 2024)

GCN ALTERNATIVE

~96.25% accuracy on same benchmarks. Treats all neighbors equally (degree-normalized aggregation). Simpler, but no per-edge interpretability for SOC triage.

❌ Lower accuracy, uniform neighbor weights ≈ no explainability

Temporal Memory: GRU vs LSTM

GRU CHOSEN

~25% fewer parameters than LSTM (2 gates vs 3). Comparable or superior performance on sequential tasks. Lower overfitting risk with limited training data.

📄 Cho et al., EMNLP 2014 · Validated by KAIROS (IEEE S&P 2024)

LSTM ALTERNATIVE

3 gates + cell state = ~33% more parameters. Theoretically handles longer sequences, but provenance temporal patterns (process lifecycles, file access) are well within GRU's capacity.

❌ No accuracy gain, higher parameter count, higher overfitting risk

Embedding Dimension: 64 vs 128

64-dim CHOSEN

177 MB for 690K node embeddings. Diminishing returns beyond 64 for provenance graphs. Total model: 61K parameters.

📄 ORCHID (arXiv 2024) finds no accuracy improvement beyond 64-dim

128-dim ALTERNATIVE

354 MB for the same 690K nodes — 2× memory. Critical because persistent GRU states must coexist with model weights during online adaptation.

❌ Double memory, negligible accuracy gain

Detection Granularity: Per-Edge vs Per-Window

Per-Edge CHOSEN

<1s target latency. Each event gets an individual score the moment it arrives. No waiting for window boundaries. Critical for catching attacks during reconnaissance.

📄 ORCHID demonstrates feasibility: 0.002s/event

15-min Windows KAIROS

Up to 15 min detection latency. Anomalous edges at start of window can't trigger alerts until window closes. Simpler implementation, but misses early attack stages entirely.

❌ Architectural latency, not computational — can't be optimized away
